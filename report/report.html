1. 課題の概要

Code as Policies（CaP, Liang et al., 2022）は、大規模言語モデル（LLM）に few-shot 例を見せて、自然言語の指示から ロボットを動かす Python コードを書かせる手法です。生成したコードをその場で実行すると、ロボットが動きます。 本課題では、公式の卓上マニピュレーションデモ（PyBullet 上の UR5e アームと 2 指グリッパーで、ブロックとボウルを動かす）を題材にして、次の 2 段階で取り組みました。

  1. CaP を Gemini API で動かす：元の実装で使われていた OpenAI text-davinci-003 は提供が終わっているため、Gemini で動くように書き直しました。
  2. CaP の蒸留：Gemini 版 CaP を「教師」にして教師データを自動で作り、手元の GPU で動く小型のコード生成モデル（生徒：Qwen2.5-Coder-Instruct）を LoRA でファインチューニングしました。生徒は few-shot 例なしの短い入力だけでロボット制御コードを書きます。

2. 目的

CaP は few-shot プロンプトが数千トークンあり、指示のたびに外部 API へ長いプロンプトを送ります。そのため、料金・レート制限・応答の遅さが問題になります。そこで、次の 3 点を調べることにしました。

  • 教師（Gemini＋few-shot）の振る舞いを、小型モデルの重みに覚えさせられるか
  • 生徒は、教師と比べてどのくらいの成功率と速さでタスクをこなせるか
  • 学習したタスクの外の指示に、生徒はどこまで汎化するか

3. システム構成

CaP は役割の異なる複数の LMP（Language Model Program ＝ LLM ＋ プロンプト ＋ 実行環境）が、お互いを関数として呼び合う構成になっています。

 指示 "put the red block in the bowl closest to it"
   │
   ▼
 tabletop_ui (LMP) ── 指示 → ロボット操作コード（say / put_first_on_second など）
   ├─► parse_obj_name      "一番近いボウル" → 'blue bowl'
   ├─► parse_position      "〜の左 10cm" → 座標 [x, y]
   ├─► parse_question      "ブロックは何個？" → 答え
   ├─► transform_shape_pts 図形の拡大・回転
   └─► fgen（LMPFGen）     コード中の未定義関数（get_closest_idx など）の本体を生成
                                  │
                                  ▼
                 PyBullet：UR5e + Robotiq 2F-85 で Pick & Place

蒸留では、LMP が「誰にコードを書かせるか」を差し替えられるようにしました（バックエンド）。教師バックエンドは few-shot プロンプト全体を Gemini に渡し、生徒バックエンドは # LMP: 名前・物体リスト・指示コメントだけからなる短い入力を、学習済みのモデルに渡します。LMP 側は、どちらのバックエンドが使われているかを区別しません。

4. 手法

4.1 Gemini 版 CaP（教師）

davinci は「続きを書く」補完型でしたが、Gemini はチャット型なので、そのまま使うとコードブロックの記号・説明文・import 文などが出力に混ざります。 そこで、システム指示で「コード補完エンジンとして、最後のコメントに対するコードだけを書く」ように指定し、さらに後処理（コードブロックの抽出・指示の繰り返しの除去・import 行の除去・stop トークンでの打ち切り）を加えて、元の CaP と同じ形の出力が得られるようにしました。

4.2 教師データの自動生成

指示文と、その指示が達成できたかを判定する関数を、シーンに合わせて自動で作る 9 種類のテンプレートを実装しました。

テンプレート指示の例成功判定
block_on_bowlput the red block on the blue bowlブロックがボウルの上にある
color_aliasput the sun-colored block on the blue bowl色の言い換えを正しく解釈できたか
cornermove the red block to the top left cornerブロックが角の付近にある
closest_bowlput the red block in the bowl closest to it最も近いボウルの上にある
extreme_blockput the left most block on the green bowl一番端のブロックが置かれた
side_ofput the red block to the left of the blue bowlボウルの左／右 4cm 以上、上下のずれ 8cm 以内
stackstack all the blocks on the green bowl全ブロックがボウルの上に積まれた
matchingput the blocks in the bowls with matching colors同じ色のペアがすべて揃った
counthow many blocks are there?ロボットの発話に正しい数が含まれる

seed からシーン（ブロック 2〜4 個・ボウル 1〜4 個）とタスクを作り、Gemini 版 CaP をシミュレーターで実行しました（150 エピソード）。成功したエピソードのコードだけを教師データにしています。 1 エピソードから tabletop_ui・parse_obj_name・fgen などの LMP 呼び出しが複数取れるので、それぞれを 1 サンプルにしました。

4.3 生徒の学習（LoRA による SFT）

項目設定
生徒モデルQwen2.5-Coder-7B-Instruct（A100、bf16）。T4 なら 1.5B を自動で選ぶ
LoRAr = 16, α = 32, dropout = 0.05、対象は全線形層（q/k/v/o/gate/up/down_proj）

5. 工夫した点

  1. チャット型 LLM を補完型として使う：システム指示と後処理の 2 段構えで、davinci 用の few-shot プロンプトを書き換えずに Gemini で動かしました。この後処理は生徒の出力にもそのまま使っています。
  2. 成功判定つきのタスク自動生成：テンプレートごとに判定関数を用意したので、人がラベルを付けなくても「成功したコードだけ」を集められます。紛らわしい配置（最も近いボウルとの距離差が 3cm 未満など）は、判定がぶれないように生成の段階で除外しました。
  3. 長時間の自動実行に耐える安全装置
    • 生成コードが届かない座標を指定すると、元の環境は無限ループします。シミュレーションのステップ数に上限を設けて打ち切るようにしました（SafePickPlaceEnv）。
    • 物体が多いと、元の配置処理は置き場所を探し続けて止まります。同じ乱数で配置を事前に試し、詰まる組み合わせは選び直すようにしました。
    • Gemini 無料枠のレート制限に合わせてリクエスト間隔を空け、429 / 5xx エラーは待ち時間を延ばしながら再試行します。1 日の上限に達したら安全に止まり、翌日に続きから再開できます（結果を JSONL に 1 件ずつ追記）。
  4. 公平な比較とデータ分割：同じ seed なら同じシーンになるので、教師と生徒を同じ条件で比較できます。検証データはエピソード単位で分け（seed が 10 の倍数）、同じシーンのサンプルが学習と検証の両方に入らないようにしました。fgen のように毎回同じ入力になる呼び出しは重複を除きました。
  5. 短い入力への置き換え：生徒は few-shot 例を読まないので、教師と比べて入力が大幅に短くなります。教師では数千トークンあった入力が、数十〜数百トークンになります。
  6. CPU / GPU ランタイムの分離：API を待つだけのデータ作成は CPU ランタイムで、学習は GPU ランタイムで行い、結果は Google Drive で受け渡すようにして、GPU の利用時間を節約しました。
  7. 提出動画の自動作成：学習済みのアダプタを読み込んでタスクを順に実行し、指示・生成コード・成否判定を映像に重ねて 1 本の動画にまとめるノートブック（CaP_Student_Demo_Video.ipynb）を作りました。

7. 考察と今後の課題

［ 結果の数値を見てから記入：生徒が教師に近づけたテンプレート／苦手なテンプレートとその原因（失敗エピソードのエラー内容から）、速度の差 ］

  • 汎化の限界：生徒が覚えたのは、9 種類のテンプレートに沿った書き方です。「三角形に並べる」のように学習データに無い種類の指示は苦手だと考えられるので、動画の最後で学習外の指示を試しています。
  • データの多様化：Gemini に指示文の言い換えを作らせたり、温度を上げて同じタスクを複数回解かせたりすれば、学習データの多様性を増やせます。
  • 失敗データの活用：今回は捨てた失敗エピソードを「悪い例」として、DPO などの選好学習に使えます。
